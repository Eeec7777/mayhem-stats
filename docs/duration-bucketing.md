# 對局長度分組

規則本體在 `cube/model/cubes/matches.yml` 與 `team_context.yml` 的 `duration_bucket`（兩邊一字不差）。
這份文件說明為什麼這樣切、怎麼驗證，以及什麼時候該重算。腳本在 `analysis/duration_bins_dp.py`、`analysis/duration_bins_cut.py`。

資料範圍：2026-08-28～10-09，533 場大亂鬥（每場至少有站長或一位追蹤對象；追蹤對象不會出現在兩隊，
所以「一場」的勝負就是這群人的勝負）。模式每個版本都在改，改版或資料多一倍後要重跑。

## 結論

| 標籤 | 為什麼 | 場數（533 場中） |
|---|---|---|
| `< 8:00（重開）` | 機制界線：最早的投降結局出現在 8:00，之前的 5 場都是 1.5～2.5 分鐘的打爆水晶，是重開或斷線 | 5 |
| `8:00-13:40` | 統計轉折：13:40 之前勝率約 68%，之後約 46% | 約 82 |
| `13:40-15:40` `15:40-17:10` `17:10-18:40` `18:40-21:00` `21:00 以上` | 轉折之後沒有其他有統計支持的結構，所以依場數等分，每段約 1/6 | 各約 80～100 |

等分的邊界是正常對局（8:00 以後）長度的 1/6 分位數，湊成好記的時鐘值：13:40（同時也是最佳單一切點）、15:40、17:10、18:40、21:00。

## 為什麼不是「每 2 分鐘切一段」

上一版（2026-10-09 之前）用固定 2 分鐘 7 段，**反而比不分段預測得更差**，是過度切分：

| 切法 | 交叉驗證 log-loss（越小越好） |
|---|---|
| 只切一刀（資料挑的最佳切點，每折重找） | **0.6892** |
| 分位數 6 等分 | 0.6932 |
| 分位數 5 等分 | 0.6944 |
| 固定 5 分鐘 | 0.6947 |
| 分位數 3 等分 | 0.6947 |
| 不分段 | 0.6952 |
| 分位數 4 等分 | 0.6954 |
| 固定 2 分鐘（上一版） | 0.6970 |

30 次重複 × 5 折，單位是每場的平均對數損失，訓練與測試以「場」切開。差距本來就不大（勝負接近丟銅板，
533 場裡能學到的結構有限），重點是**切得越細沒有變好**。

動態規劃找最佳分段（每段至少 30 場）的結果：BIC 最小的是 2 段（切點 13:30～13:40），第二、第三個切點讓對數概似只多約 0.5 與 1.1，
遠不到多一個參數的代價。

## 13:40 這個切點是真的嗎

排列檢定：把勝負打亂、長度不動，每次都**重新找最佳切點**，看最大的概似比增益有多罕見——
這樣「從很多切點裡挑了最好的」這件事已經算進去，不是只檢定一個事先決定的切點。

- 最佳切點 13.65 分（13:39），概似比增益 7.04（2×增益 = 14.1）。
- 13:40 以前 n=82，勝率 68.3%；以後 n=446，勝率 46.0%。
- 2000 次排列，p = 0.005。

Bootstrap 的切點位置很寬（90% 區間約 11:30～17:30），所以「轉折在 13:40」不要讀成精確到秒，
讀成「大約 12 到 17 分鐘之間有一個轉折」。

## 為什麼 8:00 單獨一組

最早的投降結局在 8:00 出現（8.0 分鐘有 7 場、之後陸續有），8 分鐘以前沒有任何一場是投降結束。
8 分鐘前的 5 場全是打爆水晶、1.5～2.5 分鐘，是重開或斷線，母體和正常對局不一樣，圖上列出來但不拿來和整體比。

## 怎麼讀前端的圖

敗因分析頁用勝率差森林圖，不是長條：每段一列，點是「那段勝率 − 整體勝率」，線是 Wilson 95% 區間，
**區間整段在整體的同一邊才上色**，其餘灰色。分段多就更要畫區間——每段只有幾十場，勝率的誤差可以到 ±14 個百分點。

## 因果提醒

對局長度是結果不是原因：贏的一方推得快，所以短局勝率高。這張圖是描述「什麼長度的局常是贏的」，
不是「把局打短會贏」。

## 什麼時候重算

- 資料多一倍，或遊戲改版（增幅、英雄係數、投降時間改了）。
- 執行：

```bash
uv run python -X utf8 -I analysis/duration_bins_dp.py
uv run python -X utf8 -I analysis/duration_bins_cut.py
```

- 看最佳單一切點有沒有移動、排列檢定的 p、各切法的交叉驗證排名。
- 要改界線：兩個 cube 的 `duration_bucket` 一起改；前端只吃標籤，排序靠標籤裡第一個數字，
  新標籤要維持「mm:ss 開頭」或「`<` 開頭」才排得對；測試裡 `bucketOf` 的獨立 SQL（`explore.spec.ts`、`losses.spec.ts`）跟著改。
